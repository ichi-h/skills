# Review Integrate スキル

各観点の指摘表（report-<perspective>.md）を統合し、採否を決めて findings.md にまとめる。

**このスキルの成果物は findings.md である。起票はしない。コードは 1 行も変えない。**

## 手順

1. **重複をまとめる。** 同じ指摘が複数レポートにあれば 1 件にする。
   重複は観点設計の重複であり、品質ではない。

2. **MUST の根拠を確認する。** 自分で該当ファイルの該当行を 1 回だけ読み、
   根拠が薄弱なものは落とす（誤検知）。2 度目のレビューに拡張しないこと。

3. **採否を決める。**
   - MUST / NITS: 起票対象（次のスキルに渡す）
   - IMO: プロジェクトへの効果が大きいと判断したものだけ採用
   - **落としたものも理由付きで残す。** 後から「なぜ直さないのか」を
     問い合わせられる状態にする。

4. **`未確認事項` を回収する。** レビュアーがそこに書いた 1 行は雑音ではなく、
   `evidence.md` の穴である。各行を次のように分類する。

   | 種類                             | 扱い                                                                      |
   | -------------------------------- | ------------------------------------------------------------------------- |
   | パックに入っていたが見落とされた | 何もしない。パックは正しかった。プロンプトで節を名指しすればよい          |
   | このチケットの対象外             | 理由付きで「却下」へ移す。次回また導出されないようにする                  |
   | 事実パックの本当の穴             | **次の波の前に** `evidence.md` に足す。足さないと全レビュアーが再発見する |
   | 確認できなかった本当の指摘       | 「要確認」として findings.md に運び、何が確認できれば確定するかを書く     |

   **事実パックが高いままにならないのは、この帰還ループがあるからである。**
   波の間に書き留めなかったものは、全レビュアーに再発見され再要求される。

5. **findings.md を書く。** `/tmp/review-<label>/findings.md` に次の形で。

```markdown
# {{TICKET}} レビュー統合

## 採用（起票する）

- [ ] MUST: `app/foo.ts:42` …（出典: コード / セキュリティ）
  - 起票先: {{新規 / 既存チケットの uid に追記}}

## 却下（理由付き）

- IMO: … — 品質差が小さいため却下
- MUST: … — 根拠の file:line を確認したが該当箇所に問題なし（誤検知）
- NITS: … — 既存チケット `{{uid}}` で対応中

## 未確認事項

- {{レビュアーが書いたままの行}} — {{パックに有り / 対象外 / evidence.md に追記済み / 要確認}}
```

## 完了条件

- `/tmp/review-<label>/findings.md` に全指摘の採用 / 却下と理由がある
- 全 `未確認事項` が分類され、事実パックの穴は `evidence.md` に書き戻されている
- **diff に変更が無い**
