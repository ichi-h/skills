# Review Integrate スキル

各観点の指摘表（report-<perspective>.md）を統合し、採否を決めて findings.md にまとめる。

**このスキルの成果物は findings.md である。起票はしない。コードは 1 行も変えない。**

## 手順

1. **重複をまとめる。** 同じ指摘が複数レポートにあれば 1 件にする。
   重複は観点設計の重複であり、品質ではない。

2. **MUST の根拠を確認する。** 自分で該当ファイルの該当行を 1 回だけ読み、
   根拠が薄弱なものは落とす（誤検知）。2 度目のレビューに拡張しないこと。

3. **採否を決める。**
   - MUST / NITS: 起票対象（次のスキルに渡す）
   - IMO: プロジェクトへの効果が大きいと判断したものだけ採用
   - **落としたものも理由付きで残す。** 後から「なぜ直さないのか」を
     問い合わせられる状態にする。

4. **`未確認事項` を回収する。** レビュアーがそこに書いた 1 行は雑音ではなく、
   `evidence.md` の穴である。各行を次のように分類する。

   | 種類                             | 扱い                                                                               |
   | -------------------------------- | ---------------------------------------------------------------------------------- |
   | パックに入っていたが見落とされた | 何もしない。パックは正しかった。プロンプトで節を名指しすればよい                   |
   | このチケットの対象外             | 理由付きで「却下」へ移す。次回また導出されないようにする                           |
   | 事実パックの本当の穴             | **次の波の前に** `evidence.md` に足す。足さないと全レビュアーが再発見する          |
   | リポジトリ全体に効く穴           | このパックではなく定型プロファイル `review-prepare/facts/<リポジトリ名>.md` に足す |
   | 確認できなかった本当の指摘       | 「要確認」として findings.md に運び、何が確認できれば確定するかを書く              |

   **事実パックが高いままにならないのは、この帰還ループがあるからである。**
   波の間に書き留めなかったものは、全レビュアーに再発見され再要求される。

   穴は正しい場所へ送る。このチケットで必要な事実は `evidence.md` へ、
   フレームワークやライブラリの挙動のように**このリポジトリのどのチケットでも必要になる事実**
   は定型プロファイル（`review-prepare/facts/<リポジトリ名>.md`）へ。
   1 チケットのパックに書いた穴は次のチケットでまた払う。プロファイルなら 1 回で済む。

   これを飛ばしたときのコストは、レビュアーが答えを推論して「推論」と自己申告し、統合が
   実装を読み直して決着させることになる —— しかもそのリポジトリの全チケットで答えは同じである。

   **同一原因で重大度が割れたとき。** 複数の観点が同じ原因を別の重大度で出したら、
   重大度はここで 1 回だけ決め、**原因も 1 件として記録する**（3 件起票しない）。
   そのうえで、重大度を決めた事実がパック（§3.2 の挙動、§3.3 の要求引用）にあるべきものだったかを
   見直し、あればパックか定型プロファイルへ送る。次波で同じ裁定を繰り返さなくて済む。

5. **findings.md を書く。** `/tmp/review-<label>/findings.md` に次の形で。

**レポートを再記述しない。** レポートは `findings.md` の隣に残る。段落を写すと同じ文章に
2 回払うことになり、しかも 2 つの写しが食い違っていく。書くのは判断と参照先だけ ——
主張を 1 行、深刻度、file:line、どのレポートの指摘か。背景説明（なぜ問題か、修正案）は
レポート側に置く。

```markdown
# {{TICKET}} レビュー統合

## 採用（起票する）

- [ ] MUST: `app/foo.ts:42` …（出典: コード / セキュリティ、`report-code.md` より）
  - 起票先: {{新規 / 既存チケットの uid に追記}}

## 却下（理由付き）

- IMO: … — 品質差が小さいため却下（`report-design.md` より）
- MUST: … — 根拠の file:line を確認したが該当箇所に問題なし（誤検知）
- NITS: … — 既存チケット `{{uid}}` で対応中

## 未確認事項

- {{レビュアーが書いたままの行}} — {{パックに有り / 対象外 / evidence.md に追記済み / 要確認}}
```

詳細が要るときは `file-ticket` が元のレポートを開く。参照先は `report-<観点>.md` で書き、
1 つのレポートに項目が多いときは見出しも添えて、次のスキルが直接たどれるようにする。

## 完了条件

- `/tmp/review-<label>/findings.md` に全指摘の採用 / 却下と理由がある
- findings.md にレポートの段落を写しておらず、各項目が元レポートへの参照を持つ
- 全 `未確認事項` が分類され、事実パックの穴は `evidence.md` に、リポジトリ全体に効くものは
  定型プロファイル `review-prepare/facts/<リポジトリ名>.md` に書き戻されている
- 観点間で重大度が割れたことを理由に、同じ原因を複数件起票していない
- 予算超過のまま投入された波（`DO_NOT_DISPATCH` があるのにレポートが存在する、または
  パックが 15 KB / 400 行を超えている）を見つけたら、その事実と影響を findings.md に 1 行で
  残している。「実害なし」だけで済ませない —— 静かに失敗するパターンそのものなので、
  黙って通すと次回も同じ判断が繰り返される
- **diff に変更が無い**
