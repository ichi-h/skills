# Review to Ticket スキル

観点別のレビューを並列実行し、指摘を統合し、`task-management` のチケットとして起票する。

**このスキルの成果物はチケットである。コードは 1 行も変えない。**

## 原則

- **親（オーケストレータ）はレビューするな。** 判断はすべて子エージェントに委譲する。
- **探索は 1 回、判断は並列、起票は関心ごと。** 事実収集は最初に 1 回だけ行い、
  レビュアーには判断だけをさせる。
- **指し示すな、貼り込め。** レビュアーに必要なものはすべてプロンプトに入れる
  （`path:line` 付きの事実、仕様の引用文、diff のパス）。場所を指すだけの段落は
  探索の誘因にしかならない。
- **レビュアーは 1 ターンで終わらせる。** プロンプトがレポートファイル名を明示し、
  回収はそのファイルの読み出し 1 回。「表をファイルに書け」の 2 回目のプロンプトは
  文脈全体の再送である。
- **予算はプロンプトに入れる。** スキルに書いただけの上限は動かない。
- **静かに失敗した事実は残す。** 予算超過や無視された上限は findings.md に 1 行で記す。

## 成果物ディレクトリ

`/tmp/review-<label>/` を全ステップで共有する：

```
diff.patch             # diff の唯一のコピー（ロックファイル・生成物は除去済み）
files/                 # 変更ファイルの全文（ハンクだけでは判断できないとき用）
evidence.md            # §1 チケット / §2 ファイル棚卸し / §3 検証済み事実（≤ 15 KB / 400 行）
prompt-<p>.md          # 観点ごとのプロンプト
report-<p>.md          # 各レビュアーの指摘表
findings.md            # 統合結果
status.before          # 開始時の `git status --porcelain`（完了判定用）
```

## ステップ 1 — 対象を確定し、evidence を組む

チケット uid、比較ベース `base`、受け入れ条件を受け取る。不明なら聞く。
**何を作るより先に**分割を判断する：

```bash
mkdir -p /tmp/review-<label>
git diff --shortstat "<base>...HEAD"   # 800 行超 ⇒ 関心ごとに波へ分割
git status --porcelain > /tmp/review-<label>/status.before
git diff --no-color "<base>...HEAD" -- ':(exclude)*.lock' ':(exclude)dist/*' ':(exclude)build/*' \
  ':(exclude)coverage/*' ':(exclude)node_modules/*' ':(exclude)*.min.*' ':(exclude)*.map' \
  > /tmp/review-<label>/diff.patch
git diff --name-only "<base>...HEAD"   # 変更ファイルの全文を files/ へ（生成コードは除く）
```

- 未追跡（`??`）ファイルは diff に出ない。範囲に入るものは `git add -N <path>` する。
- `evidence.md` を書く（≤ 15 KB / 400 行。diff は `diff.patch` に置く）：
  - **§1 チケット**：uid・タイトル・受け入れ条件 — **場所ではなく本文を貼る。**
  - **§2 棚卸し**：+/− 件数付きのファイル表と shortstat 1 行。
  - **§3 検証済み事実**：レビュアーが再確認しがちなものだけ — 実行して確認した挙動
    （ログの該当行）、判断が割れるフレームワーク挙動（`node_modules/pkg/file:line` まで）、
    仕様の引用文、複数観点が同じ問いを立てるときの決め手となる事実。全事実に `path:line` を付ける。
- ハンクだけでは足りないときは、該当範囲（前後 15 行程度）を §3 に貼る — ファイル全文は貼らない。

## ステップ 2 — プロンプトを組む

観点を選ぶ（1 波は最大 3。超えたら波を分ける）：

| 観点         | 必要なとき                                 | thinking |
| ------------ | ------------------------------------------ | -------- |
| Code         | 常に                                       | medium   |
| Security     | 認証・認可・外部入力・シークレットに触れる | high     |
| Tests        | テストの追加・変更がある                   | medium   |
| Architecture | 集約境界・ドメイン層・公開 API に触れる    | high     |
| Spec         | 要件・受け入れ条件が存在する               | medium   |

観点ごとに 1 つのプロンプトを `/tmp/review-<label>/prompt-<p>.md` に書く。必ず含めるもの：

1. **役割**：レビュアー。判断だけ、改修しない。成果物ディレクトリ以外は一切変更しない。
2. **対象**：チケット uid、`evidence.md`・`diff.patch`・`files/` のパス、
   自分のレポートパス `/tmp/review-<label>/report-<p>.md`。
3. **予算ブロック**（そのままコピー）：

   ```text
   ## 予算 / Budget
   - ツール呼び出しは 15 回まで。超えそうなら打ち切って、残りを「未確認事項」に 1 行で書け。
   - 全体 60 行以内。表の後に書けるのは「未確認事項:」だけ（最大 3 行）。
   - 目安 8 分。判断は evidence.md の中で完結させる。

   ## 禁止 / Prohibited
   - evidence.md の「3. Verified facts」を再検証しない。§3 が報告しているコマンドは再実行しない。
   - インタプリタ・プローブを走らせない（node -e / python -c / tsx / sqlite3 / テストランナー）。
   - ファイルの作成・編集・削除は report-<p>.md 1 つだけ。それ以外のファイルは作らない。
   - evidence.md と diff.patch を超えてリポジトリを探索しない。§3 に無いことは「未確認事項」に書く。
   ```

4. **観点の問い**：最大 4 項目。実行手順ではなく、判断すべき問いとして書く。
5. **出力形式**：
   ```text
   | Severity | Location | Finding | Evidence | Suggested fix |
   |---|---|---|---|---|
   | MUST | app/foo.ts:42 | … | … | … |
   ```
   重大度は自分の観点から付ける（MUST / NITS / IMO。最終重大度は統合側で確定する）。
   Evidence には evidence.md の節か `path:line` を書く — 根拠の無い指摘は書かない。
   指摘が無ければ `No findings` とだけ書く。

投入前に各プロンプトを自分で確認する：プレースホルダの置き忘れ、予算ブロックの有無、
レポートパスの明示。（ゲートスクリプトはもう無い — プロンプトは目視で点検できる長さまで縮んだ。）

## ステップ 3 — 並列起動、1 回待機、回収

波のレビュアー全員を**1 回の**ツール呼び出しで起動し（subagent workflow / tmux / herdr —
並列で動くものなら何でも）、全員の着地を 1 回待ってから、観点ごとに `report-<p>.md` を
1 回読む。sleep ポーリング禁止、レビュアーへの 2 回目のプロンプト禁止。レポートパスを
渡し忘れて投入したレビュアーがいれば、その出力から表を 1 回だけ自前で回収する。

## ステップ 4 — findings.md に統合する

1. **重複をマージする。** 複数レポートの同じ指摘 = 1 エントリ。
2. **MUST の根拠を検証する。** 該当行を自分で 1 回だけ読み、誤検知は落とす。
   これを第 2 のレビューにしない。
3. **accept/reject を決める。** MUST/NITS は起票対象。IMO は影響が大きいものだけ受理。
   却下したものは理由付きで残す。
4. **「未確認事項」を回収する。** レビュアーがそこに置いた 1 行は事実パックの穴であり、ノイズではない。
   分類する：パックにあった（見落とし）/ このチケットの範囲外 / 本物のパックの穴
   （次の波の前に §3 に足す）/ リポジトリ全体に当てはまる穴（スタンディングプロファイルへ、下記）/
   本物の指摘だが未確認（確認方法とともに findings.md へ）。
   観点間で重大度が割れた同じ原因は、重大度を 1 回確定して 1 回だけ記録する — そして
   その決め手の事実が §3 に入るべきだったかを確認し、次の波が同じ裁定を繰り返さないようにする。
5. **`/tmp/review-<label>/findings.md` を書く。** レポートの複述はしない。決定とポインタを記す：

   ```markdown
   # {{TICKET}} review integration

   ## Accepted (to be filed)

   - [ ] MUST: `app/foo.ts:42` … (source: code, from `report-code.md`)
     - Destination: {{new / append to existing ticket uid}}

   ## Rejected (with reasons)

   - IMO: … — rejected because the quality difference is small (from `report-design.md`)

   ## Unconfirmed items

   - {{レビュアーが書いた 1 行}} — {{分類}}

   ## Notes on the flow

   - {{予算超過、次回に持ちたいパックの穴}}
   ```

**スタンディングプロファイル。** そのリポジトリの全チケットが踏む穴（フレームワーク挙動、
ライブラリの癖）は、このスキルの隣にある `facts/<repository-name>.md` に入れる —
1 回書いて全レビューで再利用する。スキルが担うのは仕組みだけ。中身はリポジトリごとのデータである。

## ステップ 5 — チケットを起票する

`findings.md` を `file-ticket` スキルへ渡す。受理した指摘を関心ごとにグループ化し、重複を確認し、
チケットを INSERT し、findings.md に起票結果を追記する。レビューそのものを起票しない
（「検証しにくかった」はパックの穴でありチケットではない）。「要確認」の項目を修正チケットとして
起票しない — 「方針を決める」チケットのままにする。

## 予算

| 項目                             | 上限                       |
| -------------------------------- | -------------------------- |
| `evidence.md` のサイズ           | 15 KB / 400 行             |
| 1 レビューの diff                | 800 変更行（超えたら分割） |
| 1 波の観点数                     | 3                          |
| レビュアーあたりのツール呼び出し | 15（プロンプトに明記）     |
| 壁時間                           | 1 波あたり約 10 分         |

上限を超えたら素材を削るか波を分ける — 予算を下げて合わせない。

## 完了条件

- `diff.patch`・`evidence.md`・全観点の `report-<p>.md`・`findings.md` が
  `/tmp/review-<label>/` に揃っている
- 受理した全指摘が「起票済みチケット」か「既存チケットへの追記」に紐づいている
- 「未確認事項」の全行が分類済み（本物のパックの穴は §3 かスタンディングプロファイルへ書き戻し済み）
- `git status` が `status.before` と一致 — **diff に変更が無い**
